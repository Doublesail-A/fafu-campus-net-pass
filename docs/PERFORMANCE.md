# 性能与长期监测

## 先区分路径

电脑启用了FlClash TUN时，`curl --noproxy '*'` 只绕过系统HTTP代理，未必绕过TUN。浏览器可能同时受到电脑端代理与路由器中继影响。因此不能直接把电脑请求耗时归因于路由器。

监测使用三个路径：

| 路径 | 用途与限制 |
| --- | --- |
| LAN虚拟客户端 | 使用独立MAC、经过真实白名单/Squid路径，观察设备侧网络开销 |
| 路由器本机有线 | 绑定eth0及专用源端口，以临时标记跳过重复透明接入，作为本机直接建连的网络基线 |
| 127.0.0.1代理父入口 | 直接经当前共用节点，观察代理与节点侧耗时；不代表经过所有LAN识别环节 |

若本机与LAN同时慢，先看上游、目标服务和DNS；若本机快而LAN持续慢，再检查Squid/中继与负载。若只有代理慢，比较同一节点/相同测速URL、入口TCP、TLS和目标端耗时。单个样本无法排除所有瓶颈。

本机参考探针使用低于自动临时端口池的25000–25031源端口，临时OUTPUT规则仅匹配这些root本机连接。这样避免SO_BINDTODEVICE与本地UA3F重定向的回包接口冲突；不改变LAN授权或普通设备路径。规则在探针退出时删除。早期revision1有线探针未做这一隔离，其数据无效，汇总器自动剔除。

`time_appconnect`包含此前阶段；TLS阶段近似 `time_appconnect - time_connect`，首字节还包含源站处理。HTTP CONNECT代理的本地 `time_namelookup` 很小，并不意味着远端DNS没有耗时。

## 已做的开销优化

已重建的Squid HTTPS本机出站不再再次进入UA3F。仅按Squid UID与TCP443匹配，保留设备白名单、TCP重建、HTTP UA及WAN规范化规则。初期B站32项资源试验，独立建连6/12并发整批耗时改善约9–12%；HTTP/2复用整批约0.6–0.8秒，与对照基本持平。UA3F进程CPU ticks在该复用试验约减少84%，不代表整个路由器CPU降低84%。

这些数据不包含浏览器LCP、全部JS执行和滚动推荐加载；不要直接称作完整首屏打开时间。

## 安装48小时探针

这项工具针对本项目固定LAN，要求DHCP池为100–249并确认`.250`未被静态设备使用。它会添加一个明确标注“监测”的虚拟MAC，48小时到期撤销。

```sh
sh install-latency-monitor.sh
/usr/sbin/privacy-latency-monitor sample
```

root日志：`/etc/privacy-latency-monitor/log.jsonl`。每10分钟运行一次，访问B站首页、匿名nav接口、CDN脚本和GitHub；没有浏览器登录cookies。使用文件锁禁止重叠、超时和日志大小上限，到期自动移除本条cron及探针授权。路由器保持通电即可记录，不依赖电脑一直开着。

日志包含HTTP状态、curl退出码、DNS/TCP/TLS/首字节/总时间、传输字节、HTTP版本与页体验证标志。匿名B站nav返回未登录是正常业务响应；HTTP200不总意味着真正取得了首页，需结合body识别与大小。另记录主机负载、内存、conntrack和累计TCP计数。

## 两天后汇总

```sh
python3 tools/summarize-monitor.py log.jsonl
```

建议每条路径分别统计成功率、P50/P95、超时、异常页与不同时段变化。旧出口失败与同步新节点后的数据要按变更时间分开，不应混成一个成功率。

原始日志可能带有节点标签与运行信息，保留在私有目录；上传到仓库的是聚合报告。通过浏览器测试时还要记录电脑的TUN/系统代理状态、是否缓存命中和主线程长任务。无法取得浏览器权限或可信URL时应说明限制，不能把curl等同于浏览器实测。
