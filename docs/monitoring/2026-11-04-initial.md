# 2026-11-04 初步诊断与两天监测

这是当晚的初步检查，不是已完成两天监测的结论。

## 测试环境与路径

电脑启用了FlClash规则模式、系统HTTP代理与TUN；路由器当时没有设备启用手动代理。因此电脑浏览器/系统请求的GitHub路径可能包含电脑端FlClash，而不能直接当作路由器代理结果。

已查看FlClash界面配置。尝试Chrome页面实测时，自动化先报告扩展界面占用，随后桌面工具因无法可靠确认浏览器URL而拒绝继续；没有取得可信的浏览器页面性能记录。下面都是独立网络请求、路由器探针和核心状态的数据，不冒充浏览器渲染/LCP。

## 找到并处理的问题

路由器旧配置有72个节点，本轮刷新后无成功URLTest记录，通过其共用父代理访问多个目标出现连接超时。当前FlClash的98个兼容节点与路由器旧节点端点没有重合。

将当前FlClash配置中的少量节点放进**隔离、仅loopback监听**的sing-box测试，GitHub约1.16秒成功；没有切换真实设备。用户随后明确授权同步节点，正式导入98个兼容节点，保留设备分组、原有分流规则及IoT直连。旧订阅地址保留，本地文件来源按既有机制暂停远端定时覆盖。

节点文件原有的跳过节点服务端证书验证配置被保留，并由管理页继续提示；没有给网站请求添加`-k`或改变终端端到端TLS验证。
